# 27. Releases run on branches, not flags

Date: 2026-08-13

## Status

Accepted. Introduces `RELEASING.md`, `CONTRIBUTING.md`, `CHANGELOG.md`,
`scripts/version.sh` and three GitHub Actions workflows. Supersedes nothing —
before this there was no release process at all.

## Context

Fifty-six commits, one branch, **zero tags, and no CI**. Everything that had
shipped had shipped by someone building it on their own Mac, and the only record
of what a given build contained was the commit it was built from — which the
August history rewrite moved anyway, so even that pointer had already been
invalidated once.

That is survivable while one person builds and nobody else runs the result. It
stops being survivable at the first bug report against a version, because
answering "is that fixed?" requires knowing what was in the build the reporter
has, and nothing recorded it.

The question was what shape a process should take, and the honest answer depends
on something outside this repository. **Sorty is an app, not a service.** A
service can merge an unfinished feature to trunk behind a flag, ship it dark,
and switch it on per environment — the running code is always the newest code,
so the flag is what buys you the ability to merge early. An app has no such
lever. The binary a listener holds was signed weeks ago and will not change
until they update; a flag inside it can only be flipped by shipping a new build,
which is the very thing the flag was supposed to make unnecessary.

So a flag in an iOS app buys much less than it does in a service, and costs the
same: a branch in the code for every flag, two paths to test, and a cleanup
nobody schedules. Sorty already has the one flag mechanism it genuinely needs —
the `DebugLaunch` arguments, compiled out of Release entirely, which is how the
screenshot harness reaches every screen and how ADR-0005 and ADR-0006 were
measured. A second toggle layer would duplicate it for a use it does not have.

Three facts about this repository in particular shaped the rest:

**The version has exactly one home.** `Sorty.xcodeproj` is generated by XcodeGen
and gitignored, so a version set in Xcode's UI survives until the next
`xcodegen generate` and then silently vanishes. Anything that writes a version
has to write `project.yml`.

**Apple's two version fields are not one field.** `MARKETING_VERSION` accepts
one to three dot-separated integers and *nothing else*, so `0.2.0-beta.1` is
rejected at upload; and `CURRENT_PROJECT_VERSION` must strictly increase within
a version train or TestFlight refuses the build as a duplicate. A SemVer scheme
that ignores either produces a process that works until the first beta.

**Production cannot mean the App Store yet.** Sorty targets iOS 27, and App
Store submission still requires Xcode 26 and an iOS 26 SDK. Designing the
pipeline around an App Store upload that cannot happen would have meant writing
a release process nobody could run.

## Decision

**Release branches and pre-release tags. No feature flags.**

- `main` is the trunk and the dev channel. All new feature work lands there.
- `release/X.Y` is cut from `main` when a version is ready to stabilise, and
  takes **bug fixes only**. Minor-only in the name: every `0.2.x` is tagged on
  `release/0.2`.
- The newest release branch is the beta channel, tagged `vX.Y.Z-beta.N`. The
  suffix lives only in the tag; the bundle carries plain `X.Y.Z` plus a build
  number.
- A production bug is fixed on the **oldest affected release branch**, tagged
  `vX.Y.Z`, then merged forward through every newer release branch into `main`.
- Build numbers are a UTC timestamp, `YYYYMMDD.HHMM`. Not a run counter: the
  beta and release workflows are separate and would each own a counter the other
  could collide with.

Two things are deliberately advisory rather than blocking. The macOS test job
does not gate merges, because hosted runner images carry whatever Xcode Apple
has shipped them and a required check that fails for toolchain reasons teaches
everyone to ignore it. And App Store submission is not automated, because it
cannot yet succeed. Both have a written trigger for becoming real, in
`RELEASING.md`, rather than an intention.

What *does* block is a Linux job that runs in seconds: `project.yml` parses, the
version helper agrees with it, `Sorty.xcodeproj` is not tracked, and a release
tag has a changelog section to be published as its notes.

## Consequences

The version bump becomes a deliberate act with one place to do it, and a tag
that disagrees with `project.yml` is caught by CI rather than by a listener
reading release notes that describe a different build.

Merging a hotfix forward will conflict on `project.yml` **every single time** —
`release/0.1` says 0.1.1 and `release/0.2` says 0.2.0, and they cannot both be
right. The resolution is always to keep the receiving branch's version, and it
is written down in `RELEASING.md` under a warning because taking the wrong side
is silent: the branch simply starts building the older version, and the tag
check that catches it fires several merges later.

The cost of refusing flags is that a long-running feature has to be built behind
its own seams or held on a branch, and neither is free. That is the trade an app
makes, and the release branch is what it buys.

The cost of advisory CI is that a genuinely broken test can merge. This is
accepted knowingly and is the first thing to revisit: when `xcodebuild` on a
hosted runner goes green unattended, `continue-on-error` comes out of `ci.yml`
and the job becomes required. If Apple's images never catch up, a self-hosted
runner on a Mac with Xcode 27 gets there instead.
